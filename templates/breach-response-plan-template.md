# Breach Response Plan Template

Build this *before* you need it. A breach response plan written during an actual breach is a plan written under panic, with the clock already running. Fill this in, assign it to named people, and make sure those people have actually seen it.

### 2. Detection

[How breaches are typically detected in your business: monitoring alerts, customer reports, staff reports, vendor notification. Document your actual detection channels.]

### 3. Immediate steps (first 24 hours)

1. Incident lead is notified and confirms the report.
2. Technical assessment begins: what data was affected, how many data subjects, how it happened, whether it's ongoing.
3. Contain the breach where possible (revoke access, patch the vulnerability, isolate affected systems).
4. Document everything as you go, timestamps, actions taken, decisions made. You'll need this record for the NDPC notification and any follow-up.

### 4. Severity assessment

[Define what makes a breach "qualifying" for NDPC notification in your context: sensitive data involved, scale of data subjects affected, likelihood of harm. This should reflect current NDPA thresholds, verify against NDPC guidance directly since this determination is legally significant.]

### 5. NDPC notification (within 72 hours of becoming aware)

- [ ] Notification prepared covering: nature of the breach, categories and approximate number of data subjects affected, likely consequences, measures taken or proposed.
- [ ] Notification submitted to NDPC via [current official channel, verify with NDPC].
- [ ] Confirmation of submission retained.

### 6. Data subject notification

[Define when affected individuals must also be notified directly, this generally applies when the breach is likely to result in high risk to their rights. Document your criteria and communication template/channel.]

### 7. Post-incident

- [ ] Root cause documented.
- [ ] Corrective actions identified and assigned with deadlines.
- [ ] This plan reviewed and updated based on what was learned.
- [ ] If relevant, affected vendors/processors' agreements reviewed for gaps that contributed to the breach.

### 8. Plan review schedule

This plan should be reviewed [quarterly / bi-annually — set a real cadence] and after any actual incident, regardless of severity.
